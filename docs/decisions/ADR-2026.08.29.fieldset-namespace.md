## ADR-2026.08.29.fieldset-namespace — `<fieldset is="name-space" name="x">` puts structure on the wire, because the platform declined to

**Date**: 2026-08-29

**Type**: Architectural

**Context**

HTML models grouped form controls and then throws the grouping away at submission.

`fieldset` is a listed element, so it appears in `form.elements` under its own
name, and `HTMLFieldSetElement` has its own `elements` collection. Measured in
Chrome 144, two fieldsets each containing an `input name="cost"`:

    f.elements.pricing.elements.cost  -> 1
    f.elements.lease.elements.cost    -> 2
    f.elements.cost                   -> RadioNodeList of 2
    on the wire                       -> cost=1&cost=2

The namespace is a first-class object in the DOM, queryable and live. Submission
walks the form's controls in tree order and emits flat name/value pairs,
discarding it.

The omission is historical rather than considered, and it constrains the
platform far more than it constrains a library. `application/x-www-form-urlencoded`
is RFC 1866 (1995); `fieldset` arrived in HTML 4.0 (1997) as an accessibility
construct for `<legend>` and the `disabled` cascade. Nobody was going to change a
deployed wire format for a grouping element. By the time servers wanted structure they invented it themselves — and this is
the part worth stating precisely, because it is usually told as a story about
disorder. It is not divergence FROM a standard. There was never a standard to
depart from.

`key=value&key=value` is the entire specification. HTML defines no mapping from
that to any data structure, and it has no server-side parser: something on the
other end must always decide what the pairs mean. The space of key SHAPES is
undefined territory, and PHP, Rails, Python and Java each filled it because it
was empty. That they filled it differently — `a[]` versus indices, arrays versus
hashes, how deep nesting collapses — is a consequence of the vacancy, not a
corruption of anything.

Two things follow, and they are what make this decision available at all:

* **A marker EXPANDS the format rather than changing it.** No existing form emits
  a bracketed name unless an author marks a fieldset, so nothing already deployed
  changes meaning. That is the web's own ratchet — add, do not break — and it is
  why the compatibility objection applies to a bare `fieldset[name]` rule and not
  to this one.
* **Defining the grammar WHEN DECLARED is a modest, local claim**, not a bid to
  standardise brackets for everyone. A form that wants `[` to mean something else
  in its keys simply does not mark the fieldset.

The flat wire has a concrete cost, not merely an aesthetic one. Two controls
sharing a name in one form are indistinguishable in the body, and http-aware's
dirty-only PATCH filter keys `dirtyByName` by name — so one dirty control keeps
BOTH values and the server resolves the duplicate arbitrarily. Found in Circle
USP on 2026-08-29 before it shipped: three seat fieldsets each rendering
`name="member"`, an admin who touched two of them seating the wrong person
silently, with a success message naming them and the audit trail recording it as
deliberate.

**Decision**

A fieldset marked `is="name-space"` with a `name` prefixes the controls it
contains, at body-collection time.

1. **Grammar**: `subject[aspect]`. `<fieldset is="name-space" name="lease">`
   containing `name="rate"` sends `lease[rate]`. Nesting composes outward-in —
   `outer[inner][field]` — rather than nearest-wins, which is a footgun.
2. **The rename wraps BOTH the `FormData` construction and the dirty filter**, so
   `dirtyByName` is keyed on namespaced names. That is what makes the duplicate
   ambiguity impossible rather than merely inconvenient. Names are restored
   afterwards; `defaultValue`/`defaultSelected` are untouched, so dirtiness is
   unaffected by the rename.
3. **The submitter is exempt.** Its name is the ACTION INTENT — form-level, not
   field-level — and http-aware already exempts it from dirty filtering. Without
   this, an add button carrying `name="role" value="sales_rep"` inside the
   `sales_rep` fieldset would send `sales_rep[role]=sales_rep`.
4. **`fieldset[is="request-header"]` contents are exempt**, being bound out of the
   body already.

**Alternatives Considered**

- **Bare `fieldset[name]`, with no marker.** Rejected on evidence. The opt-in is
  arguably already made at the form (`is="http-aware"`), and a second signature on
  the same consent form is ceremony — but `fieldset[name]` is ALREADY IN USE with
  a different meaning inside exactly the forms the rule would govern. Circle USP's
  Financial Calculator has four named fieldsets — `pricing`, `lease`, `service`,
  `misc` — that are visual sections paired with `data-section`, inside an
  `is="http-aware"` form, live on production. A bare rule would silently rename
  every field in the heaviest PATCH consumer in that application.

  The general form of that objection outlives the specific tree: `fieldset` has
  two legitimate jobs — grouping for a human and grouping for the wire — and
  conflating them puts layout into the contract. Relabel a panel, change the API.

- **A distinct `<form-namespace>` element.** Autonomous custom elements are
  universally supported, where `is=` is not, and a separate element models the
  human-grouping / wire-grouping distinction structurally rather than by a
  marker. REJECTED, and the reason is the overlap.

  The two jobs are already separable with one element: a fieldset that is only a
  section simply is not upgraded, and fieldsets nest, so a larger section can
  contain a smaller namespace or the reverse. What a separate element buys is
  composition in both directions — and the direction actually needed is NEITHER,
  because the common case is a group that is a section AND a namespace at once.
  Two elements force a wrapper exactly there, on every ordinary use, one of the
  pair being pure scaffolding. Where the jobs coincide you want one element, and
  that coincidence is the normal case rather than the awkward one.

  A layout argument was also considered and does not survive measurement: in
  Chrome 144 `display: contents` is honoured on `fieldset` and on a custom
  element alike, so neither is more layout-transparent than the other.

- **`data-namespace`.** Rejected as the weakest of the three, not the safest.
  It is convention only — nothing upgrades it, nothing validates it, no class can
  hang off it — so it buys universal support by having no semantics to support.
  Worth knowing all the same that `is=` (customised built-in elements) was never
  implemented by WebKit and may never be universal; this library already commits
  to it with `fieldset[is="request-header"]`, and Circle USP does not target
  Safari (ADR-025). A consumer who must should note that the mechanism is
  identical under any marker and the marker is swappable.

- **Leave it to server-side convention.** That is the status quo, and the
  divergence between PHP/Rails/Python/Java bracket semantics is what makes it
  unworkable: inheriting the folklore means the notation suggests things that are
  not true, which is worse than a prefix.

**Consequences**

- **The wire can name the domain instead of the storage.** `lease_rate`,
  `lease_term_months`, `lease_company` are a namespace hand-rolled in string form
  by authors who had no mechanism for one. `lease[rate]` says the same thing in
  syntax, and — the point — survives the storage changing. Whether that value is a
  column today or reached through a join tomorrow, the contract is unchanged and
  no client notices.
- **Discoverability, in Iverson's sense.** A prefix requires the reader to already
  hold the convention; `lease[rate]` exhibits the structure to someone who has
  never seen the API, permits talking about `lease` as a unit without enumerating
  it, and proposes `/scenarios/{id}/lease` as a resource before anyone designs it.
  Uniform grammar is what makes exploration cheap: learn `subject[aspect]` once
  and parse a key you have never seen.
- **Intent is recorded in the markup, which is what makes a future divergence
  survivable.** If the platform ever gives `<fieldset name>` submission semantics,
  a marker is the seam to cut along: it distinguishes a fieldset an author meant
  to namespace from one that merely has a name, so an implementation can defer to
  the platform where the semantics agree and keep its own where they do not.
  Without it every named fieldset is the same, and there is no migration path.
- **The grammar is defined here because there is nothing to inherit**, and it is
  defined only for marked fieldsets. Pick one meaning for brackets and hold it, or
  the discoverability above becomes a lie.

- **The bracket shape is PHP's, deliberately.** It is also JavaScript's property
  access, which is why it carries: `lease[rate]` reads as indexing to anyone who
  has written `$_POST['lease']['rate']` or `obj['rate']`, and the notation is
  suggestive precisely because it borrows a mental model the reader already has
  from two directions. An invented separator would have had to earn what this
  inherits.
- **Adoption is per-fieldset, so the mechanism ships without migrating anything.**
  This is the marker's largest practical benefit and it is easy to miss among the
  principled ones. Without it, shipping the rule IS the migration: every named
  fieldset in every existing form changes meaning on the same deploy. With it, a
  new form opts in the day it is written, existing named fieldsets keep behaving
  exactly as they do, and a migration like Circle USP's `lease_*` -> `lease[*]` is
  scheduled when somebody wants it rather than forced by the mechanism landing.
  A flag day becomes an increment.

- **⚠ A rename under dirty-only PATCH fails SILENTLY.** A field whose name changes
  and whose server side has not caught up is simply absent from the body, which is
  indistinguishable from "unchanged" — no 422, no log line, just a value that
  stops saving. Adopting this on an existing form requires the markup change and
  the parser change to land together, not a fieldset at a time.

**Worked example — Circle USP's account-team panel**

The nesting resolves the one shape that looked awkward. The seat fieldset stays
an unmarked section, carrying the legend and the grid; only the add row is
upgraded:

    fieldset.team-role                              (section: legend, grid)
      figure.team-member x n                        (lines keyed {userId}[service-line])
      fieldset[is=namespace][name=sales_rep]        (namespace: the add row)
        select[name=member]
        select[name=service-line]
        button[name=role][value=sales_rep]          (submitter — exempt)

On the wire: `sales_rep[member]=<uuid>`, `role=sales_rep`. The template's fields
go back to plain names, because the structure carries the key — which is the
whole point, and the reason the hand-written `{role.key}[member]` that fixed the
defect is a stopgap rather than the answer.
