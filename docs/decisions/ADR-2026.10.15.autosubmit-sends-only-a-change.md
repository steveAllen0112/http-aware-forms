## ADR-2026.10.15.autosubmit-sends-only-a-change — an autosubmit PATCH is sent only when something has changed

**Date**: 2026-10-15

**Type**: Architectural

**Context**

`autosubmit="change"` submitted the form on every `change` from a named control. A PATCH body
states only what differs from what the server last sent or accepted (the control's default,
which `_promoteDefaults` moves to what was sent once a 2xx answers it). When nothing differed the
form still sent a PATCH, with an empty body.

The browser fires `change` for a typed value when the value is committed: on Enter, or when focus
leaves the control holding a value that differs from the one it had when focus arrived. A script
that commits a typed value itself, by stepping it (`stepUp`) or simply by firing its own
`change`, does not reset that record. The form sends the value at the script's `change`, the
server accepts it, the control is clean again, and when the person leaves the control the
browser fires its own `change`, which the form answered with an empty PATCH.

In use: a quantity box the person types into and then steps with a keyboard shortcut, before
moving on with Tab. The shortcut's PATCH carried the new quantity; the Tab's carried nothing. A
server that requires at least one field refused it with a 400; one that took an empty PATCH as a
request for the current state re-rendered the row, closing a menu or popover the person had just
opened in it.

The same thing happened while the first request was still on its way: the control was still
dirty, because its default moves only on the answer, so the browser's `change` sent the same
value again, and `requestSubmit` aborted the first request.

**Decision**

An autosubmit of a PATCH form is sent only when one of its enabled, named controls differs from
its baseline. The baseline is what the request on its way carries for that control, while there
is one, and otherwise the control's default. `requestSubmit` keeps what each request carries
(`_sent`) on record as `_pending` until that request is answered; a later request replaces the
record, and an answer clears only its own.

The rule applies to the autosubmit alone, with or without `debounce` (the delayed submit checks
when its timer runs out). A click on a submit button, `requestSubmit()` and `flush()` are
unchanged. A form of any other method is unchanged.

**Rationale**

- **"Nothing changed" is already defined for PATCH.** The dirty-only body is the library's own
  statement of what a PATCH carries; an autosubmit whose body would be empty has, by that
  definition, nothing to say. The check reads the same defaults the body is built from, so the
  two cannot disagree.
- **What is on its way counts.** Between the request and its answer, the server is about to hold
  the sent value. A commit of that same value has nothing to add; a commit of any other value,
  the rendered one included, is a change and is sent.
- **Other methods send the form whole.** For GET, POST and PUT a value set back to what the
  server rendered is a real change (a filter returned to "all" must fetch again), and the
  defaults are not kept as a record of what the server holds, since only a PATCH promotes them.
  A no-change rule there would need a baseline the library does not keep, so there is none.
- **An explicit submission is the person's or the application's intent.** A submit button, or a
  script calling `requestSubmit()`, may mean to send an empty PATCH (to have the current state
  rendered, for one); only the automatic submission is judged.

**Alternatives Considered**

- *Have the application's script stop firing `change`.* Rejected: firing `change` is how a
  script that sets a value tells the page, and the form cannot tell that `change` from a
  person's; the empty request is the form's to withhold.
- *Skip any PATCH, explicit or automatic, whose body is empty.* Rejected: it takes away a
  request an application may make on purpose, to fix a case only the autosubmit has.
- *Compare against the value at the last autosubmit, per control, for every method.* Rejected:
  that record is not the server's, and goes stale whenever a response changes a control.

**Consequences**

- One commit is one request: a value committed by a script and then by the browser on leaving
  the control is sent once, whether or not the first request has been answered.
- A PATCH form's autosubmit never sends an empty body.
- A refused PATCH (non-2xx) promotes nothing and clears its record, so the control stays dirty
  and its next `change` sends it again.
- `expectations.json` pins five cases on a PATCH form with `autosubmit="change"`: a stepped
  quantity and then Tab, a typed quantity committed by a script's `change` and then Tab, a typed
  and stepped quantity and then Tab, the same while the first request is on its way (against a
  test path answered half a second late), and a quantity stepped back to the value first
  rendered, which is sent. The harness gains step `actions` (a scripted step, a scripted
  `change`, a key press, a wait).
