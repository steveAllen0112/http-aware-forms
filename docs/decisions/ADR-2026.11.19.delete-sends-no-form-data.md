## ADR-2026.11.19.delete-sends-no-form-data — a DELETE carries nothing of the form's

**Date**: 2026-11-19

**Type**: Architectural

**Context**

Since 1.0 a DELETE was built in the same branch as GET and HEAD: the form's pairs went on the
query. Since 3.0.0 (ADR-2026.09.23.explicit-action-query-merges) they are merged into an explicit
action's own query. A form whose only purpose is to delete one thing therefore sent its fields
as well. A row's form holding a name, a quantity and a delete button sent
`DELETE /items/42?name=…&qty=…`, and an author who wanted a bare DELETE had to put the button
in an empty form of its own.

RFC 9110 §9.3.5 defines DELETE as a request "that the origin server remove the association
between the target resource and its current functionality". Of content in a DELETE it says that
it "has no generally defined semantics, cannot alter the meaning or target of the request", and
that "a client SHOULD NOT generate content in a DELETE request" without the origin server's
prior indication that it has a purpose there. The target is the whole URI, and the query is
part of it (RFC 3986 §3.4). A pair added to the query names another resource, and a cache
invalidates by the target URI (RFC 9111 §4.4), so a DELETE sent with the form's pairs on its
query clears stored responses for an address that is not the resource's own.

**Decision**

A DELETE sends no form data: no pair on the query and no body.

- It goes to the address as resolved: the submitter's `formaction`, else the form's `action`,
  with that action's own query kept byte for byte as the author wrote it.
- The form's request headers still go (`fieldset[is="request-header"]`, and every
  `requestHooks` entry). `If-Match` is the ordinary conditional delete.
- GET, HEAD, POST, PUT and PATCH are unchanged.

With no action, the address is the document's own as it stands, its query included. *Open,
to be settled before release:* whether a DELETE with no action should instead go to the
document's address without its query, as a GET leaves it when the form adds nothing.

**Rationale**

- **The address is the request.** Whatever is to be deleted is named by the URI; the form's
  fields are not part of that name, and adding them changes which resource is meant.
- **The standard says a body means nothing.** Moving the fields to a body would trade a wrong
  target for content the standard defines no meaning for, and that some implementations refuse.
- **A row's form can hold its own delete button.** The button carries `formmethod="delete"` and
  a `formaction` naming the row's resource, and needs no form of its own.

**Alternatives Considered**

- *Keep the fields on the query.* Rejected: it is the behaviour described above.
- *Send the fields as a body.* Rejected: RFC 9110 gives content in a DELETE no meaning, and
  advises a client not to send it.
- *An attribute that restores the old behaviour.* Not built. An author who needs a DELETE to
  carry the form's fields may ask for one, and it will be considered then; it is not made
  without such a request.

**Consequences**

- **This may break existing forms**, so the release that carries it is a major version, 4.0.0.
  A server that read a DELETE's query for a field the form held receives nothing now; such a
  field belongs in the action's address, which the author writes.
- A query-param fieldset composes nothing on a DELETE, since the form sends no pairs.
- `expectations.json` pins two cases: a DELETE form whose action carries a query, a field, a
  submitter's pair and an `If-Match` header, which sends the query as written, no body and the
  header; and a `formmethod="delete"` button on a GET form, which sends none of the form's
  fields. The test server answers a DELETE 204.
